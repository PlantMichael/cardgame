- Menu connection waits cancel on success, timeout, or screen exit; auth loading/result and currency callbacks stop with their controls. This fixes a reproduced eight-second timeout calling freed UI after successful connection. The exact hosted Firefox cache-related freeze still requires confirmation after publishing the new Web export.

Two-seat methodology requires deploying catalog first, then relay; hosted operation remains an operator check. Read-only Railway query: `server/tools/card-winrates.sql`. See `catalog/README.md` for limits and contract.

- Campaign mode: main-menu "CAMPAIGN" flow — a best-of-3/5/7 (Small/Medium/Large) sequence of independent local-AI matches ("nodes") against one fixed opponent deck, tracked by `CampaignState` (`scripts/game/campaign_state.gd`); some nodes carry a battlefield-wide modifier (e.g. "Dunes: all creatures have Ambush") drawn from `data/campaign_modifiers.json` via the `CampaignModifiers` autoload and applied through `GameState.node_modifier_ability` (granted to every creature played, both sides, in `play_creature()`); whoever lost the previous node picks the next flagged node's modifier from two options (main.gd's `_show_campaign_node_result_screen`), and falling 2+ node-wins behind grants a one-time extra starting mana crystal on the next node (catch-up safety net). `GameManagerAutoload.start_local_game()` takes `campaign`/`node_modifier_ability`/`grant_catchup_mana` params and routes game-over to a `Continue` button (`Board.campaign_continue_requested`) instead of the normal Play Again/ranked screen. Before the first node and again between every subsequent one, `scripts/ui/campaign_map_screen.gd` (`CampaignMapScreen`) shows a landscape trail map — all of that node's `CampaignState` nodes laid out in a zigzag path and connected by lines, color-coded won/lost/current/upcoming with a bordered "modified" marker; clicking any node previews its modifier (or "decided by whoever loses the node before this one" if not yet resolved), and a 30s countdown (or the Start Battle button) advances into `_start_campaign_match()`. Verified via the `--campaign-test`/`--tank-test` headless dev CLI hooks; the map screen's actual rendering/click behavior has not been visually verified (no GUI/screenshot tooling available in this environment) — worth a playtest.

A brief "Match Found" confirmation (opponent name + rating) shows before the game starts. - Shared health operations (`gain_max_health` / `restore_health`) own the Crypt Hunger / Apothecary / transform reaction chain; ten sites in `abilities.gd` used to open-code it and all but one skipped the transform check
- Per-match gameplay randomness (`GameState.rng`, `set_gameplay_seed`): shuffles and random targets come off the match's own generator, simulation copies carry its position, and search exploration has a separate one
- Pending choices as match state (`GameState.pending_choice` + `answer_choice`): legality computed once in the rules core, answers validated against the open choice (stale/duplicate/illegal rejected), ordinary commands blocked while one is open. Used by the three new targeted on-play effects; the older prompts have not been migrated
- Per-player network views (`to_net_dict(for_player_id)`): a client no longer receives the opponent's hand identities, only a count. A view is not a save — it carries no deck contents and no generator state
- Idempotent ranked settlement (`server/relay.js`): results carry a `match_id`, settlements are recorded in a `ranked_settlements` table, and a retry replays the stored outcome instead of moving the ladder again. The opponent's rating now comes from the server's own record of the match, not the client's claim; if both sides claim a win, neither moves Elo
- 14 new cards (handoff Part Two): Batch A's six vanilla creatures, Batch B's seven Generic creatures, and Commander Maurice with counted Reinforce
- Server-authoritative ranked matches (`specs/003-authoritative-ranked-server`, **behind `RANKED_AUTHORITATIVE`, off by default; played start-to-settlement by two scripted clients against a real relay and a real Postgres, but never by the Godot client**): ranked human-vs-human matches run their rules in a headless Godot "match host" (`scripts/game/match_host.gd`, localhost TCP + newline JSON + per-boot secret) that the Node relay spawns and supervises (`server/authoritative/host_process.js`). `server/authoritative/match_manager.js` owns seats, the command path (validate → host → **log the action row** → ack → per-seat `match_view`), the 90 s turn / 90 s mulligan / 60 s grace clocks, forfeits, abandons and resume-from-log after a host restart (a replay that misses the last logged `state_hash` voids the match with no rank change). Decks are read server-side by name from the `decks` table or `data/starters.json` and validated against the server's own card files; the seed, first seat and match id are the server's. Settlement (`server/authoritative/settle.js`) runs the existing ladder math on the **server's** result, exactly once per player via `ranked_settlements`, and `report_ranked_result` from a client is refused and audited for a server-run match. The client side is thin: `scripts/game/remote_match_client.gd` holds no rules, rebuilds the board from each `match_view` and animates from that seat's filtered events. See [Authoritative Server](authoritative-server.md)
- Server-run match capacity measured (`server/test/load.js`): 100 concurrent matches on one host process, p50 136 ms / p95 159 ms / p99 178 ms accepted-action latency against a 300 ms budget, 586 MB peak host memory (almost all of it Godot's own baseline — 10 matches cost 580 MB), ~610 accepted actions/s. No host sharding needed at the current ceiling; numbers in `specs/003-authoritative-ranked-server/research.md` §13
- Server-run ranked proven against real infrastructure: `server/test/pg_store.test.js` runs `PgStore`/`PgSettleRepo` against a real Postgres (11 checks — row round-trips with the types `resume()` expects, the `(match_id, seq)` key, settlement awarding once under a retry and under two racing transactions), and `server/test/e2e_ranked.js` plays two websocket clients through a real `node relay.js` with the flag on: register, queue on shipped starter decks, mulligan, a socket drop and rejoin mid-match, game over, the action log and spec-002 facts in the database, one settlement row per player, `report_ranked_result` refused, then a second match ended by conceding (30/30 checks). Both skip or refuse to run unless `DATABASE_URL` looks disposable. Two client-side protocol traps found doing it (the ack arrives before the view; a pending choice is visible only to the seat that owes it) are written up in `research.md` §14 — `remote_match_client.gd` handles both correctly

Not deployed anywhere yet
