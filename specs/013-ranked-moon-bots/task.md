# Automatic ranked Moon bots

Raw request: make Io, Callisto, Europa and Ganymede automatically queue ranked with normal matchmaking and rewards; let Ganymede's rating settle naturally. Preserve the established 1.0 profiles (10 tempo, 8 combo, 8 aggro, 1 weak/random) and separate bot statistics. The operator already selected Codex for this bot work. Base `fa7632d`; branch `codex/ranked-moon-bots`. Preserve the existing Crimson description and ranked_progress helper edits. Stats reset/seasons are a separate work item.

## Grounding and design

- `server/relay.js:240–284` owns the real ranked queue. It starts at ±100 Elo and widens by 60 points/second without a cap. Preserve its rules, pairing order and rewards, with no farming limits, priority overrides, rating presets or hidden matchmaking cap. Thus stronger bots can still meet Ganymede after waiting; visible bracket rank is separate from hidden Elo (`server/ladder.js:90`, Elo floor 100).
- `server/authoritative/match_manager.js:119` validates saved decks, starts canonical matches and settles through `authoritative/settle.js`. Reuse these paths for human/bot and bot/bot games, including normal Elo/rank, mulligan, timers, reconnect, forfeits, and exactly-once rewards. Do not client-report synthetic ranked wins.
- `scripts/game/moon_bots.gd` already owns drafting and style policy. A dedicated headless ranked client process will hold four ordinary WebSocket connections, one per account; it uses resume_session, save_deck, queue_ranked, match_join and match_command just like existing clients. One process limits overhead compared with four Godot processes. The client consumes only each seat's filtered match_view. For search, fill unknown hands/decks using visible counts and public priors (own known deck composition may inform its own draws), with independent deterministic planning RNG. Never use actual hidden opponent cards or draw order. Approximate beliefs are acceptable; no measured strength ordering is promised.
- `server/authoritative/schema.js` stores canonical matches. Add nullable immutable bot-profile snapshots and engine version, and use `mode: ranked_bots` when either seat has a server-owned bot identity. Existing human card/deck aggregates already select `mode: authoritative`, so real bot games stay separate without changing normal rewards. Ordinary human/human matches retain their existing mode and meaning.
- `server/bot_stats.js` and the catalog bot projector are the existing simulation aggregate owners. Extend `/data/stats/bot-matchups.json` with explicit `mode=simulation` (default/current behavior) or `mode=ranked`; never pool the two sources. Ranked source is server-verified, with an anonymous `human` participant bucket when appropriate. Humans have no exposed name/account/version/difficulty; use fixed public metadata (name Human players, version unversioned, level null, style human). Bot/version/rules/engine keys remain distinct. Historical snapshots remain unchanged. Human decks may have the normal legal 1–40 size; named bot decks are 40. Unpublished historical compositions are excluded as whole matches, like the existing human exact-deck API.

## Implementation and acceptance

1. A privileged Node worker provisions four dedicated players and issues normal session tokens, then supervises the single Godot ranked-client process. Use a server-owned `ranked_bot_accounts` mapping with unique bot/player IDs and stored current profile. Never claim or overwrite an existing human account with the same case-insensitive name. Account creation is transactional/idempotent, preserves existing bot ratings across restarts, and is not a public registration capability. Bot passwords are unknowable random hashes; tokens remain in process environment, never source/logs/CLI. Reserve the four case-insensitive names in public registration. Delete only worker-issued sessions during owned cleanup. A session advisory lock prevents two active workers controlling the same four bots; lock loss stops the child and fails for supervisor restart.
2. Each client authenticates, drafts/saves a legal public style deck, queues, joins its assigned authoritative match, mulligans/answers all choices, and plays with its existing policy and normal command rate limits. Pace actions (about 0.6 seconds) and automatically requeue after a short post-game delay. Different bots may play concurrently. Matchmaking always reads their current persisted rating. Every match_found visibly labels bot opponents (e.g. Io [Bot 1.0]) and can attach server-owned bot metadata. Clients cannot impersonate a bot by adding fields. No legacy peer-hosted bot matches: require authoritative-ranked service and fail closed when unavailable.
3. Recover closed sockets using the same token, with bounded backoff; do not send duplicate queue/save/turn commands while responses are pending. Rejoin own active match after worker/reconnect using an authenticated queue refusal containing that bot's own active match ID. Never expose someone else's match ID. Resume startup must finish before accepting new queue entries; prevent duplicate matches for one account during asynchronous pairing/reconnect. Ignore stale search completion when a newer view/sequence arrives, and derive client_seq from newly joined connection state so reconnect does not replay old commands. Normal disconnect/timeout consequences apply; do not erase losses or override ranks.
4. Bot identities, profile versions and engine version are snapshotted at match creation and survive save/reload/restart, rather than inferring historical roles from today's username. Default human stats exclude mode ranked_bots. New ranked bot stats count only finished eligible canonical results with consistent settlements for winner/loser (and genuine completed draws without rewards if supported); no voided, unfinished, contradictory or missing-settlement wins. No raw player IDs, names, match IDs or seeds in public output. Mode, cohort identities, deck/opponent relationships, bounds, caching, privacy projection and failures remain validated on relay and catalog. Existing simulation clients remain compatible when mode is omitted.
5. No special matchmaking/reward limits for Ganymede or the stronger bots. A losing real ranked bot changes Elo and rank using exactly the same math as a human; winning against one receives the normal result. A returning bot keeps its rating. No production activation, pushes, account mutations or deployment are performed as part of local source verification. Worker start is an explicit service activation, documented with required DATABASE_URL/GODOT_BIN/RANKED_BOT_URL and restart policy. Retain the existing standalone simulation worker as a separate opt-in tool.
